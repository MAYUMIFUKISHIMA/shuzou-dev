# 設計方針（未実装部分を含む）

## 構成
React + TypeScript + Vite のスマホ向けWebアプリ。Supabase Auth/PostgreSQL/RLSを追加する。GitHubにコード、SQLマイグレーション、開発設定、引き継ぎ文書を保存。設定なしは端末保存デモ。Supabase設定時は認証・キュー送信・管理画面を使用。実サービス接続は未検証。

## データモデル候補
- profiles: 個人ユーザーと役割。管理者権限を本人が変更できないこと。
- production_runs / lots: 製造のまとまり、仕込み番号、完了日時。
- lot_transfers: 混合・分割の元と先、数量、単位、日時。親子関係と物量整合性を検証。
- work_records: 入力者、作業日時、工程、ロット、測定値、改訂番号。詳細項目は帳票待ち。
- audit_events: 修正前後、実行者、日時。作業員から改変できない履歴。
- raw_material_imports / cost_entries: CSV取込単位、原価、費目、適用月、配分根拠。
- archive_exports / archive_confirmations: 出力対象と改訂、ダウンロード、社内保存確認者・日時。

帳票に依存しないprofiles、work_records、record_history、archive_exportsをSQL化済み。work_records.payloadは仮項目JSON。ロット関係や原価のスキーマは帳票確認後に追加する。

## 同期・共用端末
IndexedDBに利用者ID付きキューを保存する設計。UUIDで冪等送信し、サーバー受付後にキューを削除。端末保存失敗を必ず表示する。再送・タイムアウト・二重送信・競合をテストする。
ログアウト/切替は未送信件数を確認し、承諾後に端末内データと前のユーザーの認証状態を消す。送信中の切替を制御し、受付済みか不明な状態を無条件に「未送信」と表示しない。圏外で別ユーザーの新規ログインは保証しない。
PWAのアプリ本体キャッシュを実装済み。ユーザーデータや認証応答は共通キャッシュしない。

## 権限と削除
RLSとサーバー側処理で本人/管理者の権限を強制。入力者の付け替え、権限昇格、作業員による削除を禁止。
削除はdeleted_atによる論理削除を行い、24時間以内だけ管理者が復元可能。物理削除には関連ロット、履歴、バックアップの扱いを含めた検証が必要。
保存期限はサーバー日時で判定。製造完了から1年経過し、対象の最新版を社内保存済みであることが条件。保存確認後に修正された記録は再出力・再確認する。追跡に必要な関連記録を先に削除しない。実装前に「1年」の暦年計算と混合先の製造完了条件をテストケースで定義する。

## CSV・原価・AI
CSVはID、関連ID、単位、改訂、スキーマバージョンを保持し、復元可能な一式として出力。表計算ソフトの数式注入対策を入れる。取込は列対応の確認、事前検証、重複防止、エラー行提示を備える。
原価計算は決定的なルールで行う。費用不明を0として確定原価に見せない。予測は仕込み時点で得られる特徴だけを使い、時系列で分離した実績で評価。AIへの業務データ送信は現段階では行わない。

## 端末保存の実装状況
`src/local-store.ts` は1つのIndexedDBトランザクション内で読取・更新し、保存完了後だけUIを更新する。利用者切替時は確認したスナップショットと現状態が一致する場合のみ全未送信記録を破棄する。異なる利用者からの保存と同一IDの重複登録を防ぐ。これは認証境界ではなく、デモの競合防止。フォーカス復帰時に状態を読み直す。ブラウザデータ消去・容量回収への耐久保証はなく、サーバー未送信の実業務データにはまだ使わない。

## 接続版の実装
- Supabase Authのメール/パスワード方式。アカウント作成と役割付与は管理者がSupabase側で行う。
- `cloud-queue.ts`: デモと別DB。Web Locksで送信/破棄を直列化し、UUIDの受付確認後だけキュー削除。
- `submit_record` は冪等登録、`change_record` は改訂競合と権限・24時間期限をサーバーで検証。書込はRPCのみ許可。
- 変更履歴をサーバーで記録。全記録/履歴の固定スナップショットを作成し、CSVと完全値保持用JSONを出力。
- 1年経過による物理削除は未有効化。製造完了・混合分割・保存済み改訂判定の確定が必要。
- DBの意味的検証はPostgreSQL WASM、画面接続試験は模擬API。実Auth/PostgRESTは別途検証が必要。
